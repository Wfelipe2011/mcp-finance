## ADDED Requirements

### Requirement: forecast_predictions table stores ML predictions per tenant per category per month
The system SHALL provide a Postgres table `forecast_predictions` that stores monthly spending predictions generated by the ML worker for each tenant, category, and future month.

#### Scenario: Table structure supports 3-month forecast per category
- **WHEN** the ML worker inserts predictions for a tenant
- **THEN** `forecast_predictions` contains rows with columns: `id`, `tenant_id`, `category_pt`, `group_pt`, `target_year`, `target_month`, `predicted_amount`, `lower_bound`, `upper_bound`, `model_version`, `status`, `created_at`, `updated_at`
- **AND** `status` is one of: `'ok'`, `'insufficient_data'`

#### Scenario: UPSERT prevents duplicate predictions
- **WHEN** the ML worker runs again for the same tenant and month
- **THEN** existing rows are updated (not duplicated) via UPSERT on `(tenant_id, category_pt, target_year, target_month)`

### Requirement: forecast_model_meta table stores training metadata per tenant
The system SHALL provide a Postgres table `forecast_model_meta` that records training outcomes per tenant per run.

#### Scenario: Metadata captured after each training run
- **WHEN** the ML worker completes training for a tenant
- **THEN** `forecast_model_meta` records: `tenant_id`, `trained_at`, `months_of_history`, `num_categories`, `mae`, `mape`, `status`, `error_message`
- **AND** `status` is `'ok'` when training succeeded or `'insufficient_data'` when skipped
